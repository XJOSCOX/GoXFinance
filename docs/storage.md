# Storage architecture and migration plan

## Current desktop storage

GoXPlan's React screens call the `FinanceStore` interface in `src/lib/storage.ts`. The Tauri 2 desktop implementation uses the maintained Tauri SQL plugin with SQLite. Desktop data is written to `goxplan.sqlite` in Tauri's per-user app configuration directory for `com.goxplan.desktop`; it never requires a network service. The legacy Dexie adapter is lazy-loaded only in the browser development build or when the user explicitly checks the desktop WebView's old IndexedDB.

SQLite migration `0001_initial.sql` creates the requested entity tables, UUID text primary keys, household foreign keys, relationship indexes, and schema version tracking. `0002_reconciliation.sql` adds bank balance confirmations, account-linked payments, transfers, saved scenarios, and balance correction history. `0003_variable_paychecks.sql` adds pay types, work-period and actual-pay fields, a unique source/work-period index, and paycheck correction history. These are additive migrations; no database reset or deletion is part of the upgrade. Migration 3 infers hourly pay type for older income sources with an hourly rate and variable pay type for variable-frequency sources without one. Existing amounts and transactions remain intact.

Money columns end in `_cents` and use `INTEGER`. The TypeScript adapter rejects sub-cent values and values outside JavaScript's safe integer range. APR, hours, and overtime multipliers are non-monetary `REAL` values. Timestamps are ISO 8601 UTC text (for example, `2026-10-18T12:00:00.000Z`); dates without times use `YYYY-MM-DD`. The initial household UUID is a local placeholder and becomes an ownership key in a future multi-household design. SQLite `PRAGMA` commands and Tauri's migration registration are storage mechanics; financial calculations remain in TypeScript.

The tables include `household_members`, `income_sources`, `income_transactions`, `income_transaction_revisions`, `expenses`, `expense_transactions`, `debts`, `debt_payments`, `settlement_offers`, `settlement_payments`, `bank_accounts`, `bank_transfers`, `savings_goals`, `trading_accounts`, `trading_transactions`, `monthly_budgets`, `categories`, `saved_scenarios`, `balance_corrections`, and `application_settings`. Every table is now mapped through the desktop storage adapter. `expense_transactions` stores both actual expenses and scheduled one-time expenses with distinct kinds. `trading_transactions` stores dated actual payouts separately from non-cash trading activity. Payments linked to an offer go in `settlement_payments`; other payment records go in `debt_payments`.

The Tauri command `apply_finance_batch` executes related writes inside one SQLite transaction and validates foreign keys before commit. Paycheck confirmations have a unique source and work period. Editing a confirmed paycheck appends old and new integer-cent snapshots to `income_transaction_revisions`; changing a verified debt or bank balance appends to `balance_corrections`. Neither audit collection can be edited or deleted from the UI. Account and debt confirmation dates are required for new verified balances.

## Existing IndexedDB records

Browser IndexedDB is origin and profile scoped. A Tauri WebView cannot access the database of a separate browser origin. The browser preview uses transient memory, and offers an explicit export of older IndexedDB records from the same origin. The desktop also offers an explicit check for IndexedDB in its own WebView. Import validates schema versions, record IDs, cent precision, and foreign-key references; previews collection counts and UUID/work-period conflicts; then merges within one transaction using the chosen skip, update, or review policy. The source IndexedDB is never deleted. Keep the old store and the exported JSON until counts and important balances are verified in SQLite.

Native SQLite snapshots use the online SQLite backup API. Restore validates integrity and schema version, then merges inside a transaction with foreign-key validation. It does not overwrite or delete current rows. Snapshots live beside the database in an app-owned `backups` directory and are **not encrypted**. Optional AES-GCM encryption is available for portable JSON backups. Local database encryption and an optional app lock remain future work; they require a key management design, migration of the existing plain database, and a recovery plan.

## Future PostgreSQL / Supabase path

Keep the `FinanceStore` interface and add a separate PostgreSQL implementation. Define PostgreSQL migrations separately: map `0002` balance/transfer/scenario tables and `0003` pay type, paycheck periods, unique period index, and revision table to native `UUID`, `BIGINT` cents, `TIMESTAMPTZ` for timestamps, `DATE` for calendar dates, `DOUBLE PRECISION` or bounded `NUMERIC` for hours, boolean columns, and PostgreSQL check constraints. The partial unique paycheck index translates to PostgreSQL `CREATE UNIQUE INDEX ... WHERE source_id IS NOT NULL AND work_period_start IS NOT NULL AND work_period_end IS NOT NULL`. Keep UUIDs and versioned record changes so re-imports and sync operations are idempotent. Before any cloud rollout, introduce explicit household membership and ownership, a conflict policy based on record version and timestamps, authentication, and row-level security keyed by household membership. Test cross-household isolation in PostgreSQL. Cloud sync and authentication are disabled; there are no Supabase keys or credentials in this project.

The current SQL plugin stores its SQLite file in Tauri's app configuration directory. If a future release moves it to a different OS-specific data directory, that release must perform a one-time verified file migration and retain a recoverable copy. Do not simply change the connection URL.
