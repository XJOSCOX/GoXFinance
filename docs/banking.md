# Bank connectivity and transaction reconciliation

## Stage A — schema and authorization

Additive migration 0029 creates separate bank connections, account access assignments, dated balance observations, import batches, provider/inbox transactions, review requests, reconciliation links, transfers, refund adjustments/allocations, merchant rules and audit records. It adds compatible unique indexes to existing bill/debt payment identifiers; no financial records are replaced. Startup's existing verified backup gate runs before pending migrations. Migration tests reopen both SQLite modes and compare every existing table row.

Money is an exact safe integer in cents; date-only transaction dates remain YYYY-MM-DD and timestamps use UTC ISO-8601. Accounts and references use UUIDs; provider identifiers are opaque backend references. Monetary CHECK constraints reject fractional SQLite values. PostgreSQL can use UUID, BIGINT, timestamptz/date and equivalent FK/unique/check constraints in separate migrations; service logic does not depend on SQLite SQL.

Only the protected household Owner can create/edit bank profiles, hide accounts, assign access or record balance observations. Other active linked members see only explicitly assigned accounts. Admin does not imply bank access. Account observations do not create income, spending, bank transfers, assets or debt payments. Credit-card balances are liabilities, not cash. Mapping an account to an existing asset/debt is explicit and unique; mapped balances are not added automatically to net worth.

Banking API responses are whitelisted and never include stored access tokens, token ciphertext, token key identifiers or provider account IDs. There are no hard-delete routes. Existing data, authentication and encryption settings remain intact. External connectivity and accounting approvals will be enabled in subsequent independently tested stages; no live Plaid activity is authorized.

## Stage B — manual imports and inbox

Bank accounts and Transactions are separate sidebar pages. Owners create manual profiles, record append-only balance observations and assign account visibility. Statement import supports mapped CSV and a limited, closed-STMTTRN OFX/QFX parser; external entities/DTDs, excessive statements, ambiguous dates and fractional cents are rejected. Account currency must match. Raw statements and full account numbers are not persisted; reference identifiers are hashed, and long numeric identifiers in descriptions are masked.

Preview selects valid rows, skips previously imported fingerprints, requires explicit selection/confirmation of possible same-date/same-amount duplicates, and rejects stale account previews. Identical legitimate rows within one statement remain distinct. Submission keys, transactional duplicate checks and audit writes prevent repeated or partially saved imports. Unreviewed/pending transactions never create accounting entries. Imported data remains available after restart in plaintext and encrypted databases. Suggestions are explainable keywords only at this stage; final accounting review and existing-record matching are added in Stage D.

Fictional QA verified account creation, CSV mapping, signed preview amounts and inbox persistence at localhost:1421; no real account or statement was used. OFX support deliberately ignores institution account headers and does not support every vendor extension. CSV remains the fallback.

## Stage C — Sandbox connectivity

Install dependencies with `npm install`. Set `PLAID_ENABLED=true`, `PLAID_ENV=sandbox`, and your own Sandbox `PLAID_CLIENT_ID` / `PLAID_SECRET` in the ignored backend `.env`, then restart the launcher. Use Bank accounts → Connect Sandbox bank. React Plaid Link loads from Plaid only after this explicit action. Complete Link with fictional Sandbox credentials; the backend exchanges the temporary public token. Sync Now previews the currently available provider history; confirmation saves account observations, inbox transactions and the persisted cursor atomically. History length depends on Plaid/institution availability. Nothing becomes accounting automatically.

Only Transactions is initialized. The official Node SDK calls Link, token exchange, cached `/accounts/get`, `/transactions/sync`, and `/item/remove`. No paid Balance endpoint, optional product, refresh call, webhook, tunnel, payment initiation or transfer API is enabled. Unsupported investment/loan accounts and zero-value provider events are excluded. Pagination retries restart at the original persisted cursor; pages are held in memory until confirmation. Preview expiry/revision checks reject concurrent changes. Pending/posted relations are preserved across pages. Provider modifications/removals flag reviewed records rather than deleting accounting links; unnecessary removed merchant text is redacted.

Permanent tokens are AES-256-GCM encrypted with a separate 32-byte application key, fresh nonces and household/connection authenticated context. Windows DPAPI CurrentUser protects that key at `%LOCALAPPDATA%/GoXFinance/keys/plaid-token-key.dpapi`. No key bytes travel in command arguments, logs or responses. Keep this protected file with your Windows recovery material; ordinary database backups do not contain it. It is tied to the Windows user/machine security context and is not a portable recovery key. Losing the matching protected key disables connectivity; restore the original key and Windows profile, or disconnect the Item through Plaid and reconnect after reviewing capacity. The API blocks new connections and sync if an existing token uses a different key. Non-Windows/failed protected storage fails closed. Manual imports continue working.

The local Sandbox reservation cap is conservatively 1–10 across this database, not per household. Reservations are persisted before Link starts. Failed, abandoned and uncertain attempts consume capacity; update mode does not create a new slot, and disconnect never restores one. Backup rollback or another installation can make local counts incomplete. Plaid's Dashboard remains authoritative. These controls cannot prevent charges if somebody externally upgrades a Plaid account.

**Live connections are disabled in code, even if `PLAID_ENV=production` is configured.** Before any future activation: independently confirm the team's free Trial eligibility, Transactions entitlement and lifetime Items already created in Plaid Dashboard; confirm a $0 plan with no paid upgrade; obtain the user's separate explicit authorization; then implement/review a production-only entitlement gate with the authoritative baseline, cap and expiry before enabling a production SDK base path. If no free Trial is available, retain Sandbox/manual imports. No live test runs automatically.

Automated tests inject a fictional Sandbox gateway and separately verify the official SDK request contract. They exercise both SQLite modes, encrypted token reopening, wrong keys, actual Windows DPAPI persistence, pagination mutation retries, pending replacements, modified/removed records, idempotency, rollback, account scope, Owner controls, reauthorization, lifetime cap and removal. A real Plaid Sandbox Link session still needs developer-provided Sandbox credentials; none were read or created for QA.
