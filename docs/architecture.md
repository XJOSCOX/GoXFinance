# Architecture

- `apps/web/src/app`: routing and authentication/household gates. `features/auth` owns account screens, API client, and session state. `features/households` owns setup, join, member, and invitation views plus selected-household state. `features/dashboard` composes the household Overview from authenticated API data. `features/bills` and `features/expenses` separate API clients, data-loading hooks, forms, lists, and detail views. Reusable visual components and accessible notifications live in `components/ui`; the preserved dark palette is in `styles`.
- `apps/api/src/modules/auth`: routes declare endpoints, controllers translate HTTP/cookies, the service handles identity and sessions, and the repository is the auth query layer. `modules/households` separates routes, controllers, services, permission guards, and repositories. Each household operation checks the authenticated user's role on the backend. Invitation redemption derives member, household, and role exclusively from the stored invitation. Signup with a code inserts the user and links their member/role in one SQLite transaction; existing users use an authenticated redemption endpoint. `middleware/csrf.ts` enforces same-origin writes. `config` and `db` own configuration and connection lifecycle.
- `packages/shared`: Zod input contracts, public types, and household role permissions shared by website and API. No password hashes or session secrets appear in public types.
- `packages/db`: Drizzle SQLite schema and versioned migrations. IDs are UUID text and timestamps use UTC ISO 8601 strings; optional household move-in dates use `YYYY-MM-DD`. Session expiration uses Unix seconds. Migrations are applied on API startup. Migration `0001` adds household tables, `0002` adds invitations and a member lookup constraint, `0003` adds optional household details, and `0004` adds planned roles, requests, audit, and Owner guards. Migration `0004` uses `ALTER TABLE` and backfills planned roles from pending invitations or active regular roles without replacing existing members. It adds SQLite triggers for immutable creator, Owner role, and Owner member record; PostgreSQL will need equivalent protections in its own migration.

Migration `0005` adds `debts` and `debt_members` without rebuilding existing tables. The latter uses composite foreign keys so a responsible member belongs to the debt's household. Amounts use integer cents and nullable values distinguish unknown amounts from zero. APR is decimal text. The debt service checks role, creator, member responsibility, and Owner-exclusive access on every write. The repository commits a debt and its member associations in one transaction. Shared debt calculations group records only when a link is verified and count each joint obligation once. Member amounts are labeled as associations, not separate amounts owed. The website calls the debt API and does not query SQLite directly.

Migration `0006` adds `debt_payments`, immutable `debt_balance_history` entries, and `debt_payment_audit`. Composite foreign keys keep payments and statements in the same household as their debt. Payment creation uses a unique idempotency key; status changes, edits, and cancellations retain before/after audit snapshots in the same transaction. A new verified balance is appended to history and updates the debt's recorded balance only if it is at least as recent as the current verification. The shared payment calculation uses the latest dated verification and completed payments after that date. It subtracts known principal only; an unknown principal or missing verified baseline produces an unknown estimate. A completed payment on the statement date also makes the estimate unknown because date-only records cannot establish posting order. The estimate does not model unreported interest or fees.

Migration `0007` adds `debt_change_requests` and `debt_change_audit`, and adds a nullable unique request key to balance history. Existing tables and records remain intact. Admins/Editors authorized to manage a debt shared with the protected Owner may propose payment edits, cancellation, confirmation, or a verified balance. Requests do not modify financial records. Only the Owner may approve/reject. Approval rechecks the requester’s current permissions and compares a snapshot fingerprint before applying the exact proposed change. Financial changes, request completion, and audit writes share an immediate SQLite transaction; a failure rolls all of them back. Requesters can withdraw pending proposals. Duplicate submissions replay the stored request, and duplicate/stale approval is rejected. The Owner sees a household-wide approval queue on Debts; each debt also has an Approvals tab.

Migration `0008` extends those requests to account edits, archiving, and restoration. Direct account writes are blocked for every non-owner when any responsible member is the protected household creator. Eligible Admins/Editors can submit a reason and a sparse account proposal, including responsible-member changes; only the Owner applies it after review. Owner-exclusive debts remain Owner-only and Viewers remain read-only. Current balance and verification-date corrections still use Balance History, including its existing approval workflow. SQLite cannot widen existing CHECK constraints in place: this new migration transactionally recreates the request table and its audit child while copying every row with its original identifiers and keeping foreign-key enforcement enabled. Earlier migrations are unchanged. See [owner-debt-permissions.md](owner-debt-permissions.md) for the policy and verification results.

`db/sqlite-backups.ts` creates WAL-safe snapshots using `VACUUM INTO`, validates integrity, foreign keys, and known migration fingerprints, and restores with SQLite’s supported backup API. Pending migrations on an existing debt database trigger a verified pre-migration snapshot. Manual recovery endpoints require an authenticated user who owns every household and whose households include every other account; they never return filesystem paths or database downloads. Restore requires the exact confirmation phrase, pauses writes, and is applied on API restart while the server holds an exclusive runtime lease. A recovery snapshot is retained and restored sessions are invalidated. See [recovery.md](recovery.md) for steps and limits.

The new website database is `data/goxfinance_web.sqlite`; old desktop SQLite files stay in their existing location. The site does not import old finance records or use browser databases. Login state is rechecked through `GET /api/auth/me` on page load.

Registered users and household members are separate records. A role links a registered user to a household and is unique for that user and household. A member can optionally link to a registered user. The first household creation transaction inserts its household, Owner role, and linked member together. Duplicate setup for an already assigned user returns the existing household. Owner/Admin/Editor/Viewer permissions live in `packages/shared`; only the Owner can directly add members, manage roles, or issue invitations. Admins and Editors submit requests that the Owner approves or rejects; approval creates a member and audit row in one transaction. Requests and permission changes are audited without invitation secrets. A planned role on an unlinked member is not an active permission. Changing it atomically revokes pending invitations. Invitations are linked to an approved member and store only a hash of the high-entropy code. A nullable unique active-member key allows one pending invitation per member while retaining revoked, expired, and redeemed history. Claiming a code conditionally links the member, assigns its stored role, and marks the code redeemed in a transaction. Inactive or already-linked members cannot be claimed.

For future Supabase PostgreSQL support, define a separate Drizzle PostgreSQL schema and migrations, map the existing UUID IDs and UTC timestamps, and move the repository implementation to the PostgreSQL driver. Keep service and HTTP contracts unchanged. Plan a versioned, audited data migration with duplicate prevention before moving any user records. Supabase credentials, sync, and authentication are intentionally absent.

Bills and everyday expenses use separate normalized tables and services. The Overview service composes the shared expected-obligation and actual-outflow calculations; route handlers contain no database queries. Bill approvals reuse the debt workflow conventions, and linked debt payment writes also check bill permissions. See [bills-expenses.md](bills-expenses.md) for accounting rules, migrations, permissions, and limits. A shared Prettier configuration and reusable UI primitives keep new modules readable without a feature-specific CSS layer.

Payment forms share amount selectors, optional breakdown fields, clearance review, and exact decimal parsing. Bill payment status/allocation storage is extended by migration `0013`; historical identifiers and links are preserved. Completed debt creation also checks Owner-linked modification permissions. See [payment-options.md](payment-options.md).
