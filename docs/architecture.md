# Architecture

- `apps/web/src/app`: routing and authentication/household gates. `features/auth` owns account screens, API client, and session state. `features/households` owns setup, member pages, forms, API calls, and selected-household state. `features/dashboard` owns the empty authenticated screen. Reusable visual components live in `components/ui` and `components/layout`; the preserved dark palette is in `styles`.
- `apps/api/src/modules/auth`: routes declare endpoints, controllers translate HTTP/cookies, the service handles identity and sessions, and the repository is the auth query layer. `modules/households` separates routes, controllers, services, permission guards, and repositories. Each household operation checks the authenticated user's role on the backend. `middleware/csrf.ts` enforces same-origin writes. `config` and `db` own configuration and connection lifecycle.
- `packages/shared`: Zod input contracts, public types, and household role permissions shared by website and API. No password hashes or session secrets appear in public types.
- `packages/db`: Drizzle SQLite schema and generated, versioned migrations. IDs are UUID text and timestamps use UTC ISO 8601 strings. Expiration uses Unix seconds. Migrations are applied on API startup. Migration `0001` adds `households`, `household_members`, and `household_user_roles` with foreign keys and indexes; it does not alter the existing auth tables.

The new website database is `data/goxfinance_web.sqlite`; old desktop SQLite files stay in their existing location. The site does not import old finance records or use browser databases. Login state is rechecked through `GET /api/auth/me` on page load.

Registered users and household members are separate records. A role links a registered user to a household and is unique for that user and household. A member can optionally link to a registered user. The first household creation transaction inserts its household, Owner role, and linked member together. Duplicate setup for an already assigned user returns the existing household. Owner/Admin/Editor/Viewer permissions live in `packages/shared`; the API applies them through service guards, and member writes cannot assign access roles. Role assignment and invitations have no public endpoints yet.

For future Supabase PostgreSQL support, define a separate Drizzle PostgreSQL schema and migrations, map the existing UUID IDs and UTC timestamps, and move the repository implementation to the PostgreSQL driver. Keep service and HTTP contracts unchanged. Plan a versioned, audited data migration with duplicate prevention before moving any user records. Supabase credentials, sync, and authentication are intentionally absent.
